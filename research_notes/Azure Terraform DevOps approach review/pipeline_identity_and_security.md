# Pipeline identity and security model for the Azure DevOps Terraform pipeline (as of October 2026)

Design under review, from `pipelines/` and `bootstrap/` in this repo:
- There is one service connection per environment (`andes-sc-<env>`). Each one uses manual workload identity federation (WIF) and is backed by a user-assigned managed identity (UAMI) that lives in the tfstate resource group.
- The UAMI has Contributor on the environment's resource group (RG). It also has Role Based Access Control Administrator on that RG, with an ABAC condition that limits both role-assignment *write* and *delete* to an allowlist: Key Vault Secrets User/Officer, Storage Blob Data Contributor/Reader and Monitoring Metrics Publisher. Finally, it has Storage Blob Data Contributor on its own state container.
- One service connection is used for the PR plan, the main-branch plan, the apply and the SQL-grant stage.
- Approvals and the exclusive lock sit only on the Azure DevOps Environment (`andes-<env>`), which only the apply deployment job references. The service connection itself has no checks.
- The secret `allowedIpAddresses` is a JSON list in variable group `andes-vg-<env>`. It is mapped to `TF_VAR_allowed_ip_addresses` in the plan step. The saved `tfplan` is published as a pipeline artifact whenever the plan has changes, including on PR runs.

## Q1. Workload identity federation for Azure DevOps service connections: GA status, recommendation, managed identity vs app registration, limitations

### Takeaway
**Verdict: confirms the current design.** WIF is GA (Sprint 234, early 2024) and is Microsoft's recommended method for Azure Resource Manager service connections. Secrets, certificates and agent-assigned managed identities are kept only for backward compatibility. A UAMI backing the connection is an explicitly supported and recommended option. CAF says a UAMI integrates more easily with IaC/vending than an app registration, and a managed identity's token lifetime (about 24 hours) helps with long jobs. The repo's manual "draft, then federated credential, then Verify and save" flow is exactly Microsoft's documented manual flow. Two current items need tracking:
- The Azure DevOps OIDC issuer is moving to the Entra issuer; the old issuer retires on July 1, 2027.
- Unused service connections are auto-disabled after 100 days, which matters for rarely deployed qa/prod connections.

### Cited Findings
- Microsoft's current ARM service connection doc says: "We recommend using workload identity federation with either an app registration or managed identity. Workload identity federation eliminates the need for secrets and secret management." Non-WIF options (secret-based app registration, agent-assigned managed identity, publish profile) "are available for backwards compatibility and edge cases and not recommended." — [Connect to Azure with an ARM service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure)
- On manual setup, the same doc says "Manual configuration is more time consuming than the automatic configuration and should only be used if you've already tried to automatic option". It lists "Managed identity ... [connected] to an existing user-assigned managed identity" as a recommended option "when you don't have permission to create an app registration." — [Connect to Azure with an ARM service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure)
- GA: "Workload identity federation for Azure Resource Manager service connections is now generally available" (Sprint 234 release notes, 2024). The public preview was in Sprint 227 (Sept 2023). — [Sprint 234 update](https://learn.microsoft.com/azure/devops/release-notes/2024/pipelines/sprint-234-update#features); [Sprint 227 update](https://learn.microsoft.com/azure/devops/release-notes/2023/pipelines/sprint-227-update#features)
- Security rationale from the preview announcement: "there's no persistent secret involved in the communication between Azure Pipelines and Azure. As a result, tasks running in pipeline jobs can't leak or exfiltrate secrets that have access to your production environments." — [Sprint 227 update](https://learn.microsoft.com/azure/devops/release-notes/2023/pipelines/sprint-227-update#features)
- Sprint 246 (2024) added managed identity support and made a recommendation: "To prevent sharing over-privileged managed identities, it's recommended to use a managed identity with workload identity federation instead of managed identities assigned to agent pools." The managed identity "can be different from the subscription the service connection accesses." — [Sprint 246 update](https://learn.microsoft.com/azure/devops/release-notes/2024/pipelines/sprint-246-update#features)
- The "Secure your Azure Pipelines" series says: "Use workload identity federation instead of a service principal for your Azure service connection whenever feasible." — [Secure agents, projects, and containers](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/misc)
- CAF: "Implement OpenID Connect (workload identity federation) authentication with federated credentials for the identity. Never use client secrets or certificates." CAF also says: "User-assigned managed identities are managed by Azure Resource Manager. Application registrations (service principals) are managed by Entra ID. User-assigned managed identities more easily integrate with your subscription vending process, ensuring they're decommissioned along with your other resources when no longer needed." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- Microsoft documents the manual managed-identity flow in this order: "Create the managed identity... Create the service connection in Azure DevOps and save as a draft... Add a federated credential... Grant permissions... Save your service connection." The last step is "Select Finish setup... Select Verify and save." The manual wizard offers only **Subscription / Management Group / ML Workspace** scope levels. There is no resource-group field, so RG scoping comes from RBAC on the identity. — [Manually set an ARM workload identity service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/configure-workload-identity)
- The automatic managed-identity flow does have an optional "Resource group for service connection" field, described as "Enter to limit managed identity access to one resource group". — [Connect to Azure with an ARM service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure)
- Issuer change: "Workload identity federation service connections that use the Azure DevOps issuer (`https://vstoken.dev.azure.com`) are deprecated and will retire on July 1, 2027. New workload identity federation service connections use the Microsoft Entra issuer (`https://login.microsoftonline.com/`) by default." — [Manually set an ARM workload identity service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/release/configure-workload-identity). The new subject format is `<entra prefix>/sc/<organization id>/<service connection id>`, which replaces `sc://org/project/name`. — [Sprint 253 update](https://learn.microsoft.com/azure/devops/release-notes/2025/pipelines/sprint-253-update#features)
- Inactivity: "Azure Pipelines might automatically disable connections that you didn't use for 100 days." — [Connect to Azure with an ARM service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure)
- Token lifetime: on `AADSTS700024` errors after about 1 hour, Microsoft advises using "Workload identity federation and a Managed Identity instead. Managed Identity tokens have a lifetime of around 24 hours." — [Troubleshoot workload identity service connections](https://learn.microsoft.com/azure/devops/pipelines/release/troubleshoot-workload-identity?view=azure-devops#error-messages)
- The azurerm provider supports exactly the repo's pattern. It uses `ARM_OIDC_REQUEST_TOKEN`/`ARM_OIDC_REQUEST_URL` and otherwise falls back "on `SYSTEM_ACCESSTOKEN` and `SYSTEM_OIDCREQUESTURI`". "The ADO service connection ID is required ... via environment variable `ARM_ADO_PIPELINE_SERVICE_CONNECTION_ID` ... For users of the AzAPI provider AzureRM will also fall back on `ARM_OIDC_AZURE_SERVICE_CONNECTION_ID`." The guide also warns: "If the `ado_pipeline_service_connection_id` value is not set ... the provider [falls] back on the GitHub OIDC authoriser instead," and "at least one task in the pipeline has Service Connection support and has your service connection specified." — [terraform-provider-azurerm OIDC guide (source)](https://github.com/hashicorp/terraform-provider-azurerm/blob/main/website/docs/guides/service_principal_oidc.html.markdown)
- For comparison, the ALZ accelerator's Azure DevOps Terraform template uses a different method. It passes the task's one-shot `idToken` as `ARM_OIDC_TOKEN` instead of letting the provider request fresh tokens. — [ALZ terraform-plan.yaml helper](https://github.com/Azure/accelerator-bootstrap-modules/blob/main/alz/azuredevops/pipelines/terraform/templates/helpers/terraform-plan.yaml)

### Inferences
- The repo's approach (manual WIF, UAMI in a separate RG, `ARM_ADO_PIPELINE_SERVICE_CONNECTION_ID` + `SYSTEM_ACCESSTOKEN` so the provider and backend refresh tokens) matches current Microsoft and HashiCorp guidance. It is more robust for long applies than ALZ's one-shot `ARM_OIDC_TOKEN`.
- Trade-off: putting `System.AccessToken` into the Terraform process means any provider, module or `external` program in the run can mint new OIDC tokens for that service connection for the rest of the job. It can also call Azure DevOps REST APIs as the build identity. This raises the stakes for running untrusted PR code with this connection (see Q4). Two mitigations reduce the token's reach: setting the job authorization scope to the current project, and keeping the build service's permissions minimal.
- Connections created after the Sprint 253 change already use the Entra issuer. The bootstrap passes in whatever issuer/subject the draft shows, so it should be compatible, but this is not verified against a live run. Any older connection must be converted before July 1, 2027.
- qa/prod connections that see no traffic for 100 days may be auto-disabled, so this belongs in the runbook.

### Gaps
- I found no Microsoft doc that says "Verify and save" fails when the identity has only RG-scoped rights, and none that documents a current "save without verification" option for WIF connections. The docs show only "Verify and save". Whether verification succeeds with RG-only Contributor (it needs the subscription to be readable/listable by the identity) is not documented. It should be confirmed empirically, or the docs left as is.
- Microsoft does not rank managed identity above app registration in general. Both are "recommended"; the managed identity preference comes from CAF's IaC/vending argument and the token-lifetime note.

## Q2. Least privilege: Contributor on the RG plus ABAC-conditioned Role Based Access Control Administrator vs Owner / User Access Administrator

### Takeaway
**Verdict: confirms; this is the Microsoft-recommended pattern.** Microsoft names Owner/User Access Administrator as the old, over-privileged way to delegate role assignment. It recommends **Role Based Access Control Administrator with conditions ("constrained delegation")**, scoped as narrowly as possible (RG rather than subscription). The repo's condition covers both write and delete for an allowlist of roles, which is the documented pattern. Optional hardening Microsoft documents but the repo does not use: restricting **principal types** or **specific principals**, for example so the pipeline cannot grant data roles to itself.

### Cited Findings
- Problems with Owner/UAA delegation: "Delegate has unrestricted access at the role assignment scope. This violates the principle of least privilege... Delegate can assign any role to any user within their scope, including themselves. Delegate can assign the Owner or User Access Administrator roles to another user." "Instead of assigning the Owner or User Access Administrator roles, a more secure method is to constrain a delegate's ability to create role assignments." — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- Constrained delegation: "Delegating role assignment management with conditions is a way to restrict the role assignments a user can create or delete... you can constrain the roles that [the delegate] can assign, constrain the principals that [the delegate] can assign roles to, and constrain the role assignments [the delegate] can remove. This delegation with conditions is sometimes referred to as *constrained delegation* and is implemented using Azure attribute-based access control (Azure ABAC) conditions." — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- The same page lists benefits that apply directly to pipelines: "You can prevent a delegate from allowing another user to assign roles... You can automate the management of Azure resources without having to grant full permissions to a service account." — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- Role choice: "The Role Based Access Control Administrator role is a built-in role that has been designed for delegating role assignment management to others. It has fewer permissions than User Access Administrator, which follows least privilege best practices." "You can select any role that includes the `Microsoft.Authorization/roleAssignments/write` action, but Role Based Access Control Administrator has fewer permissions." — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- Documented ways to constrain assignments: by roles; by roles plus principal types (user/group/service principal); by roles plus specific principals; and with different conditions for add vs remove. — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- Known issue: "You can't have a role assignment with a Microsoft.Storage data action and an ABAC condition that uses a GUID comparison operator." This doesn't affect the repo, because RBAC Administrator has no storage data actions. — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)
- RBAC best practices: "If you must assign a privileged administrator role, use a narrow scope, such as resource group or resource, instead of a broader scope, such as management group or subscription. If you are assigning a role with permission to create role assignments, consider adding a condition to constrain the role assignment." — [Best practices for Azure RBAC](https://learn.microsoft.com/en-us/azure/role-based-access-control/best-practices)
- Service connection scope: "Avoid granting broad contributor rights for the entire Azure subscription. When creating a new Azure Resource Manager service connection, always choose a specific resource group." — [Secure agents, projects, and containers](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/misc). CAF: "Scope the identity permissions to only the Azure subscription or resource groups required for deployment." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- For contrast, the ALZ accelerator (platform landing zone, not workload) gives the **apply** identity **Owner** at the intermediate root management group, and the plan identity Reader at the same scope. — [ALZ accelerator Permissions FAQ](https://azure.github.io/Azure-Landing-Zones/accelerator/faq/permissions/); [bootstrap variables.tf `role_assignments_terraform` default](https://github.com/Azure/accelerator-bootstrap-modules/blob/main/alz/azuredevops/variables.tf)
- Microsoft's Azure DevOps Terraform OIDC sample gives the apply identity "contributor access to the resource group" and the plan identity "read only access to the resource group". — [Azure-Samples/azure-devops-terraform-oidc-ci-cd README](https://github.com/Azure-Samples/azure-devops-terraform-oidc-ci-cd)

### Inferences
- For a workload RG, the repo is stricter than the ALZ accelerator's defaults: Contributor + constrained RBAC Admin at RG scope instead of Owner at management-group scope. It matches the RBAC best-practice text.
- Residual risk: the allowlist includes **Key Vault Secrets Officer/User** and **Storage Blob Data Contributor/Reader**, and the condition does not restrict *principals*. So the pipeline identity, or any code running under it, can grant itself data-plane access to every vault and storage account in the RG. Microsoft's doc explicitly offers principal-type and specific-principal constraints for this. One example is an ABAC clause that excludes the pipeline's own principal ID, or restricts assignments to `ServicePrincipal`/`Group`. Note that dev assigns roles to developer principals (`developer_principal_ids`), so a principal-type restriction would need care.
- Contributor alone already allows data-path escalation in practice (for example, deploying code to an App Service that runs as the app's managed identity). The ABAC condition stops escalation to *control-plane ownership*, not to data access. This is another reason to keep untrusted PR code off this identity (Q4).

### Gaps
- I found no Microsoft doc that prescribes this exact "Contributor + conditioned RBAC Admin" combination for Terraform pipeline identities. The conclusion is drawn from the general RBAC delegation and best-practice docs plus the CAF/Azure-Samples patterns.

## Q3. Separate identities per environment (blast radius)

### Takeaway
**Verdict: confirms, and adds one more requirement.** CAF, the azurerm provider guide and Microsoft's Azure DevOps Terraform sample all recommend one identity and one service connection per environment, which the repo does. CAF goes further and asks for **a separate read-only identity per application and environment** for Terraform plan. The repo does not have that yet (Q4).

### Cited Findings
- CAF (general): "Create a separate identity for each application and environment you deploy to, ensuring granular permissions can be applied. Create a separate identity per application and environment for read-only operations, such as Terraform plan or Bicep what-if." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- CAF (Azure DevOps): "Create a separate service connection and identity for each application and environment you deploy to... Ensure your identity federated credentials are scoped to the service connection only. Deploy your service connections through infrastructure as code (IaC) in a secure subscription vending process." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- CAF application identity guidance: "You shouldn't share credentials or managed identities among various environments or applications. For example, don't use identities for production resources and also in dev/test resources... Create separate credentials for each instance of an application to reduce the likelihood of a compromised test instance affecting production data." — [CAF: Application identity and access management](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/identity-access-application-access#design-recommendations)
- HashiCorp azurerm guide: "An application or managed identity requires a federated credential for each Azure DevOps service connection. In common scenarios, there will be one registration/identity per environment with one credential for the environment's service connection." — [azurerm OIDC guide (source)](https://github.com/hashicorp/terraform-provider-azurerm/blob/main/website/docs/guides/service_principal_oidc.html.markdown)
- Microsoft sample: "The bootstrap creates separate plan and apply identities and service connections per environment... This is to implement the principal of least privilege." — [Azure-Samples/azure-devops-terraform-oidc-ci-cd](https://github.com/Azure-Samples/azure-devops-terraform-oidc-ci-cd)
- Microsoft's Owner/UAA delegation warning lists "Delegate can assign any role to any user within their scope, including themselves" as a core risk. This supports keeping the pipeline identity outside any scope where it holds role-assignment rights. — [Delegate Azure access management to others](https://learn.microsoft.com/en-us/azure/role-based-access-control/delegate-role-assignments-overview)

### Inferences
- The repo's pattern of a per-environment UAMI in a separate tfstate RG, created by admin bootstrap, so the pipeline cannot modify its own identity, matches CAF's "separate identity per environment" and "deploy identities via a secure vending process" guidance. CAF does not mention keeping the identity outside the RG it manages, but that follows directly from the RBAC escalation concerns in Q2.
- The one gap against CAF is the missing read-only identity per environment.

### Gaps
- CAF does not say whether the per-environment *plan* identity should also live outside the managed RG. By analogy it should, to keep the same tamper-resistance.

## Q4. PR plans with write-capable credentials; separate plan (read-only) and apply identities; forks vs same-repo branches

### Takeaway
**Verdict: contradicts the current design.** The "future improvement" should be treated as current best practice, not optional. CAF explicitly says to create a separate read-only identity per environment for Terraform plan. The ALZ IaC accelerator and Microsoft's Azure DevOps Terraform OIDC sample both create separate **plan** (Reader) and **apply** (Owner/Contributor) identities and service connections, and use the plan connection for PR/CI runs. HashiCorp states that `plan` can execute arbitrary code and that "the plan permission is equivalent to the write permission".

In Azure DevOps, PRs from **same-repo branches** run the PR's own YAML with full access to service connections and secret variable groups. Only **fork** PRs are denied secrets by default. So today anyone who can push a branch to the GitHub repo can run code, through Terraform providers/`external`/`local-exec` or simply an edited YAML step, as the write-capable identity, **before any review and without touching the Environment approval**.

Two practical caveats apply even with a separate plan identity:
1. In both ALZ and the sample, the plan identity still gets **Storage Blob Data Contributor on the state container** (needed for state locking), so it can tamper with state.
2. Built-in Reader has only `*/read`, so plans that read `list*` actions or data-plane data may need a small custom role.

### Cited Findings
- CAF: "Create a separate identity per application and environment for read-only operations, such as Terraform plan or Bicep what-if." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- The ALZ accelerator overview lists for Azure DevOps: "Service Connections with Workload identity federation for Plan and Apply", "User Assigned Managed Identities (UAMI) with Federated Credentials for Plan and Apply", separate Plan and Apply environments, "Service Connection Approvals, Template Validation and Concurrency Control", and "Group and Members for Apply Approval". — [Azure Landing Zones IaC accelerator](https://azure.github.io/Azure-Landing-Zones/accelerator/)

### Inferences
- **Concrete risk in the current design.** A same-repo PR can do any of the following in the plan stage, which runs *before review*, using `andes-sc-<env>`. The ADO Environment approval never comes into play, because the plan stage doesn't reference the Environment.
  1. Change `steps-terraform.yml` or the plan script to run `terraform apply` or arbitrary `az` commands.
  2. Add a malicious provider/module, a `data "external"`, or a `local-exec` (on a resource that would be created).
  3. Exfiltrate `SYSTEM_ACCESSTOKEN` to mint OIDC tokens for the connection.

  Because the identity holds Contributor + conditioned RBAC Admin + state write, the result could be resource destruction, data-plane self-grants (Q2) or state tampering. GitHub branch protection with required reviewers on `main` does not mitigate this, because the PR pipeline runs before the merge.
- **Recommended target model,** consistent with CAF, ALZ and the Azure-Samples sample:
  - Per environment, a `plan` UAMI and connection with Reader on the RG (plus any narrowly needed read/list or data-plane read roles) and blob access to the state container.
  - An `apply` UAMI and connection with the current Contributor + conditioned RBAC Admin.
  - PR runs and the plan stage use only the plan connection. Apply and the SQL-grant stage use the apply connection.
  - Approvals, branch control (`refs/heads/main`) and optionally required-template checks go on the **apply service connection** (Q5).
- **State-write caveat.** Even ALZ's plan identity can write state, because the azurerm backend takes a blob lease for locking. Options:
  - Accept this, as ALZ does.
  - Give the PR plan identity Storage Blob Data Reader and run PR plans with `-lock=false`.
  - Keep main-branch plans on a lock-capable identity.

  None of these is documented by Microsoft as a recommendation. They are trade-offs.
- **Reader-coverage caveat.** Several azurerm resources call `list*` actions during refresh, such as listing keys and web app settings. Pure Reader can then fail with 403. This repo disables shared keys/local auth, which may reduce such calls but probably not eliminate them (web app config). Expect to need a small custom "plan reader" role.
- Alternative or additional mitigation if a read-only identity is deferred: require a team-member comment for **same-repo** PRs too (now possible per source, Sprint 275), so no PR plan runs before a trusted reviewer has looked at it.

### Gaps
- I found no HashiCorp page that specifically says "use read-only credentials for plan and write credentials for apply" for Azure. HashiCorp's guidance is the general "plan = write" / arbitrary-code statement. HCP Terraform dynamic credentials reportedly support separate plan/apply identities, but I did not verify this for this note.
- I found no Microsoft document listing which azurerm resources fail under Reader. The 403-on-`list*` caveat is inferred from the Reader definition and was not confirmed against a primary source.
- I found no Microsoft statement on how ALZ/the sample justify giving the plan identity Storage Blob Data Contributor on state.

## Q5. Azure DevOps Environments, approvals/checks, exclusive lock and branch control for Terraform apply

### Takeaway
**Verdict: partially contradicts the current design.** Putting approvals and the exclusive lock on the ADO Environment is a valid ADO feature, but current CAF guidance is explicit: "Create approvals on the service connection. Don't create them on environments, as that can be bypassed in code." CAF also asks for **required templates** on the service connection. "Secure your Azure Pipelines" asks for **branch control checks on service connections**. ALZ puts the apply approval, exclusive lock and required-template checks on the service connections, and Microsoft's sample deliberately leaves the environment without checks so "the approval is to use the identity and cannot be bypassed".

Today the repo's service connection has no checks, and it can't have approval or branch control as long as PR plans use it. That is the structural reason the separate plan connection (Q4) is needed.

### Cited Findings
- CAF (Azure DevOps identities): "Create approvals on the service connection. Don't create them on environments, as that can be bypassed in code. Create required templates (also known as governed pipelines) on the service connection to ensure that malicious code can't be injected without approval." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- Secure your Azure Pipelines: "Restrict service connections to specific branches: Use a branch control check to limit which branches can use your service connection. Having a branch control check ensures that service connections only run on authorized branches and all linked pipeline resources are built from allowed branches." — [Secure your Azure Pipelines](https://learn.microsoft.com/azure/devops/pipelines/security/overview?view=azure-devops#restrict-project,-repository,-and-service-connection-access)
- How checks work:
  - "Approvals and other checks aren't defined in the yaml file. Users modifying the pipeline yaml file can't modify the checks performed before start of a stage."
  - "Checks enable the *resource owner* to control if and when a stage in any pipeline can consume a resource."
  - "Checks can be configured on environments, service connections, repositories, variable groups, secure files, and agent pools."
  - Check order: static (Branch control, Required template, Evaluate artifact), then pre-check approvals, then dynamic checks, then post-check approvals, then Exclusive lock.

  — [Define approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)
- Branch control: "ensure all the resources linked with the pipeline are built from the **allowed** branches and that the branches have protection enabled... You can also define the behavior of the check if the protection status for one of the branches isn't known." "The check requires the branch names to be fully qualified... `refs/heads/<branch name>`." — [Define approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)
- Exclusive lock: "allows only a single run from the pipeline to proceed... `runLatest` - Only the latest run acquires the lock to the resource. `runLatest` is the default if no `lockBehavior` is specified. `sequential` - All runs acquire the lock to the protected resource sequentially." — [Define approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)
- Approvals: "Specify if you want to permit or restrict approvers from approving their own runs"; "If a group is designated as an approver, only one user within the group needs to approve." — [Define approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)
- The 2024 GA release notes describe the intended production pattern: "you can specify that only pipelines that run on the `main` branch of a repository are allowed to use a production ARM service connection. Furthermore, you can require human approval." — [Sprint 234 update](https://learn.microsoft.com/azure/devops/release-notes/2024/sprint-234-update#azure-pipelines)
- ALZ implementation: an approval check on the **apply** service connection (`requester_can_approve = length(var.approvers) == 1`, 12-hour timeout), plus exclusive-lock and required-template checks on both plan and apply service connections. Templates are pinned to `refs/heads/main` of a separate templates repository. — [service_connections.tf](https://github.com/Azure/accelerator-bootstrap-modules/blob/main/modules/azure_devops/service_connections.tf)
- Microsoft sample: approval "is enforced on the prod-apply service connection". The environment is left unconfigured by design "to ensure that the approval is to use the identity and cannot be bypassed". Pipelines "are stored in a separate repository to the code they deploy", which "allows you to govern the pipelines and ensure that only approved templates are used". "The required template check will ensure that the pipeline is using the template specified in the template repository." — [Azure-Samples/azure-devops-terraform-oidc-ci-cd](https://github.com/Azure-Samples/azure-devops-terraform-oidc-ci-cd)
- Service connection authorization: "Selecting **Grant access permission to all pipelines** ... isn't recommended. Instead, authorize each pipeline individually." The repo already follows this. — [Connect to Azure with an ARM service connection](https://learn.microsoft.com/en-us/azure/devops/pipelines/library/connect-to-azure)

### Inferences
- An Environment approval gates only jobs that reference that Environment. Any stage in a modified YAML that uses `andes-sc-<env>` directly (as the plan and SQL stages already do) skips it. CAF's "can be bypassed in code" warning refers to exactly this.
- Recommended configuration, once plan and apply connections are split:
  - **Apply connection**: Branch control `refs/heads/main` (with "verify branch protection" chosen deliberately, because protection status for GitHub branches may be reported as unknown); Approval (restrict self-approval for qa/prod); Exclusive lock (`lockBehavior: sequential` if every merged plan should apply in order, or the default `runLatest` to skip superseded runs); optionally Required template.
  - **Plan connection**: Exclusive lock is optional. Required template is optional but useful, because it stops a PR from replacing the steps that use the connection.
  - The Environment can stay for deployment history and visibility.
- Required template is strongest when templates live in a separate repo/ref that PR authors can't change (ALZ/sample pattern). In a single-repo setup it adds less protection.
- Terraform's own state lock plus the saved-plan staleness check already stop two applies from corrupting state. The exclusive lock mainly gives orderly queueing and avoids failed "stale plan" applies.

### Gaps
- I found no Microsoft doc that confirms how branch-control "branch protection" verification behaves for **GitHub** repos (vs Azure Repos). The doc only says the behavior when status is unknown is configurable.
- CAF doesn't say whether approvals on the apply service connection should replace or add to Environment approvals. The ALZ/sample pattern shows "on the service connection" as the primary control.

## Q6. Secret variables in variable groups vs Key Vault-linked groups; env mapping; plan-artifact exposure

### Takeaway
**Verdict: partially confirms.**
- **Matches guidance:** explicit `env:` mapping of the secret to `TF_VAR_*`, a secret variable group authorized per pipeline, and marking the Terraform variable `sensitive`.
- **Microsoft prefers** Azure Key Vault for secrets (a Key Vault-linked variable group or the Key Vault task). Plain library secret variables are acceptable but second choice.
- **Contradicts guidance:** storing the value as a **JSON list**. Microsoft says "Don't use structured data as secrets", because substrings (individual IPs) are not masked in logs.
- **Plan files** contain variable values in cleartext, so HashiCorp says to treat them as sensitive. The repo publishes `tfplan` as a pipeline artifact on PR runs too, which widens exposure.

### Cited Findings
- Secret mapping: "Unlike a normal variable, they are not automatically decrypted into environment variables for scripts. You need to explicitly map secret variables." "Never pass secrets on the command line. Instead, we suggest that you map your secrets into environment variables." — [Set secret variables](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/set-secret-variables)
- Substring masking: "We never mask substrings of secrets... For this reason, secrets should not contain structured data. If, for example, "{ "foo": "bar" }" is set as a secret, "bar" isn't masked from the logs." — [Set secret variables](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/set-secret-variables)
- "Don't use structured data as secrets: Avoid using structured data formats like JSON, XML, or YAML to encapsulate secret values... Instead, create individual secrets for each sensitive value." — [Secrets in Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/secrets)
- Key Vault preference: "Secrets present inherent security risks, so it's best not to use them at all." "It's best to securely manage secret variables in Azure Key Vault. You can also set secret variables in the pipeline definition UI or in a variable group." On limiting access: "Store your secrets in Azure Key Vault. By using Azure Key Vault, you can use Azure role-based access control to limit access to a secret or group of secrets... Set secrets in variable groups. Variable groups follow the library security model." — [Secrets in Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/secrets)
- CAF: "Always avoid using secrets... In the case that you can't avoid using a secret... Set up a secret store such as Azure Key Vault, and reference the store in Azure Pipelines." — [CAF: Security considerations for DevOps platforms](https://learn.microsoft.com/en-us/azure/cloud-adoption-framework/ready/considerations/security-considerations-overview)
- Key Vault-linked groups: "Only the secret names map to the variable group, not the secret values. When pipelines run, they link to the variable group to fetch the latest secret values from the vault at runtime." The doc also says "RBAC key vaults behind private endpoints are not supported by Azure DevOps", and that the service connection needs Get/List or **Key Vault Secrets User**. — [Link a variable group to secrets in Azure Key Vault](https://learn.microsoft.com/azure/devops/pipelines/library/link-variable-groups-to-key-vaults?view=azure-devops)
- Branch-limiting secrets: "To ensure that secrets are accessible only to a certain repository branch, you can use a combination of branch policies, variable group permissions, and conditional job insertion." Variable groups can also take checks such as branch control. — [Secrets in Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/secrets); [Define approvals and checks](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)
- Logging commands: "Don't use a logging command to set a secret variable, because anyone who can access your pipeline can also see the secret." — [Secrets in Azure Pipelines](https://learn.microsoft.com/en-us/azure/devops/pipelines/security/secrets)
- Saved plan files: sensitive values hidden in terminal output are still "saved in cleartext in the plan file"; "the file does contain your full configuration, all of the values associated with planned changes"; "You should therefore treat any saved plan files as potentially-sensitive artifacts." — [terraform plan command](https://developer.hashicorp.com/terraform/cli/commands/plan)
- HashiCorp: marking a variable sensitive "will not prevent it from being read by Terraform during plan or apply operations", and providers/modules have "full access to the variables". — [HCP Terraform security model](https://developer.hashicorp.com/terraform/cloud-docs/architectural-details/security-model)

### Inferences
- The JSON-list secret (`["203.0.113.10", ...]`) is exactly the structured-secret anti-pattern. If Terraform or `az` ever prints a single IP, for example in an error message, it won't be masked. Terraform's `sensitive` flag mitigates normal plan output but not every error path. Options:
  - Store each IP as its own secret.
  - Accept that the IPs are low-sensitivity data that only needs to stay out of the repo, and document that explicitly.
- Key Vault-linked groups would add Azure RBAC and auditing, but they need an ARM service connection with Secrets User on the vault. Keep that vault outside the RG the pipeline manages, so the pipeline can't grant itself access to it. For a low-sensitivity value like developer IPs, a library secret is a reasonable, documented choice.
- Plan artifact exposure: PR runs also publish `tfplan-<env>` when there are changes. Each PR plan therefore becomes a downloadable artifact holding the cleartext IP list (and any other variable values) for anyone with artifact read access in the project, for the pipeline's retention period. Two mitigations:
  - Publish the plan only on `main` (PR runs don't need the artifact, because apply never runs on PRs).
  - Keep retention and project read access tight.
- With a separate PR plan identity, also consider whether PR runs need the secret at all. Without it, a plan would fail ("No value for required variable"), so either keep the group on PR runs, accepting the same-repo branch exposure described in Q4, or provide a non-secret placeholder for PR plans.

### Gaps
- I found no Microsoft doc that specifies who can download pipeline artifacts by default in a private project. The exposure inference assumes the standard project-reader access model and was not verified here.
- I found no Microsoft or HashiCorp guidance written specifically for "secret Terraform variable in an ADO variable group vs Key Vault" beyond the general secret-handling docs cited above.
