# Automating per-environment bootstrap (identities, state, Azure DevOps setup) for Terraform on Azure — state as of October 2026

Context: the repo currently bootstraps each environment with imperative PowerShell (`bootstrap/New-TfStateBackend.ps1` once per subscription; `bootstrap/New-AppEnvironment.ps1` twice per environment). The second pass exists only to add the federated identity credential once the admin has copied the issuer and subject from a hand-made draft service connection (see `C:/Users/Rorro/source/repos/azure-terraform/bootstrap/New-AppEnvironment.ps1` lines 21–28 and 189–207: parameters `-AdoFederationIssuer` / `-AdoFederationSubject`). The recommendation under review: replace `New-AppEnvironment.ps1` and the manual Azure DevOps steps with an admin-run Terraform root module (azurerm + azuread + microsoft/azuredevops), one map entry per environment, and keep the PowerShell state-backend script.

## Q1. Does microsoft/azuredevops support a WorkloadIdentityFederation service connection backed by a user-assigned managed identity, exporting issuer/subject usable in the same apply? Is the "private preview" note stale? Which other resources exist, and how does the provider authenticate?

### Takeaway
Yes. `azuredevops_serviceendpoint_azurerm` accepts `service_endpoint_authentication_scheme = "WorkloadIdentityFederation"` with a UAMI's client ID and exports `workload_identity_federation_issuer` / `workload_identity_federation_subject`, which feed `azurerm_federated_identity_credential` in the same apply. Microsoft's own ALZ bootstrap module does exactly this in production. The "private preview" note is stale: WIF for ARM service connections went GA in Azure DevOps Sprint 234 (early 2024). The docs are also out of date in a second way you didn't mention. Azure DevOps now issues new WIF connections from the Microsoft Entra issuer, with a subject that contains the service connection's GUID. So the subject can't be predicted in advance, and reading the provider's computed outputs is the only reliable option.

### Cited Findings
**Service connection resource (WIF + UAMI)**
- The provider docs list `WorkloadIdentityFederation`, `ManagedServiceIdentity` and `ServicePrincipal` as allowed values for `service_endpoint_authentication_scheme`; the default is `ServicePrincipal` "for backwards compatibility". `serviceprincipalkey` is "not required if `service_endpoint_authentication_scheme` is set to `WorkloadIdentityFederation`", but `credentials.serviceprincipalid` is still set, and in the WIF example it is the UAMI's `client_id`. — [azuredevops_serviceendpoint_azurerm docs (GitHub source of the registry page)](https://github.com/microsoft/terraform-provider-azuredevops/blob/main/website/docs/r/serviceendpoint_azurerm.html.markdown)
- The same page has an example that creates an `azurerm_user_assigned_identity`, a WIF `azuredevops_serviceendpoint_azurerm`, and an `azurerm_federated_identity_credential` whose `issuer`/`subject` come from the endpoint's `workload_identity_federation_issuer` / `workload_identity_federation_subject` attributes, with audience `api://AzureADTokenExchange`. — [same page](https://github.com/microsoft/terraform-provider-azuredevops/blob/main/website/docs/r/serviceendpoint_azurerm.html.markdown)

### Inferences
- Because the Entra-issuer subject contains the service connection GUID, nobody can compute it before the connection exists. Wiring `azuredevops_serviceendpoint_azurerm.*.workload_identity_federation_subject/issuer` into `azurerm_federated_identity_credential` is therefore the robust design, not just a convenience. It also works for organizations still on the old issuer, because the provider passes through whatever Azure DevOps returns (PR #861 reads the API's authorization parameters; ALZ relies on the same behaviour, see Q3). Terraform orders the dependency, so the two-pass flow disappears.
- For an admin-run bootstrap, `use_cli = true` (the default) with the admin's `az login` avoids PATs entirely. That fits the repo's "no secrets anywhere" convention better than the PAT the ALZ accelerator asks for (Q3).
- Before 2027-07-01, any connection still on `vstoken.dev.azure.com` must move to the Entra issuer. With Terraform owning the connection, there are two options. One is converting in the portal and letting the next plan refresh the computed issuer/subject, which would update the FIC. The other is tainting and recreating the connection, which changes its GUID and therefore the subject, and then re-applying. Either way Terraform repairs the FIC automatically, which the PowerShell flow can't do.
- Approvals and checks can attach to the ADO Environment (`azuredevops_environment` + `azuredevops_check_approval`) or directly to the service connection. Microsoft's ALZ module puts its checks on the service connections (Q3). That protects the identity no matter which pipeline or stage references it, so it's worth copying.
- Variable groups in this design should hold only non-secret values: client IDs, subscription IDs, backend settings. Any secret variable managed by Terraform would land in the bootstrap state (the import note implies values are tracked). If secrets ever appear, Key Vault-linked groups keep them out of state.

### Gaps
- I couldn't find an explicit statement from the provider maintainers on what v1.16.0 returns for `workload_identity_federation_issuer/subject` on an organization using the Entra issuer. The pass-through behaviour is inferred from the API docs and the ALZ code, not from provider tests.
- I found no provider doc saying whether `azuredevops_serviceendpoint_github` supports GitHub App authentication, or only PAT/OAuth. That matters only if the bootstrap also creates the build definitions; check the `serviceendpoint_github` page before including pipelines.
- The azurerm docs don't say whether changing `issuer`/`subject` on `azurerm_federated_identity_credential` forces replacement. It matters only for the issuer migration and is harmless either way.

## Q2. hashicorp/azuread for Entra security groups and members: what permissions does the running identity need?

### Takeaway
A user principal needs the Groups Administrator, User Administrator or Global Administrator directory role; a service principal needs `Group.Create` plus a read permission for the member types it adds. In tenants that haven't restricted group creation, ordinary users can also create security groups, but the azuread docs list the admin roles as the requirement. The running principal becomes the group's sole owner by default, which matters for later management.

### Cited Findings
- "When authenticated with a service principal, the least privileged permissions that are required are: `Group.Create` and `User.Read.All`, `Application.Read.All` or `Directory.Read.All`". `User.Read.All` is needed for users as owners/members, `Application.Read.All` for service principals as owners/members, and `Directory.Read.All` for either. — [azuread_group docs](https://github.com/hashicorp/terraform-provider-azuread/blob/main/docs/resources/group.md)
- With `assignable_to_role`, the resource "additionally requires the `RoleManagement.ReadWrite.Directory` application role". — [azuread_group docs](https://github.com/hashicorp/terraform-provider-azuread/blob/main/docs/resources/group.md)
- "When authenticated with a user principal, this resource requires one of the following directory roles: `Groups Administrator`, `User Administrator` or `Global Administrator`". For administrative units, Groups Administrator must be scoped to the unit. — [azuread_group docs](https://github.com/hashicorp/terraform-provider-azuread/blob/main/docs/resources/group.md)
- "By default, the principal being used to execute Terraform is assigned as the sole owner." "Groups cannot be created with no owners or have all their owners removed." `prevent_duplicate_names` defaults to `false`, and "Group names are not unique within Azure Active Directory." — [azuread_group docs](https://github.com/hashicorp/terraform-provider-azuread/blob/main/docs/resources/group.md)
- Microsoft's Graph Bicep quickstart says that, by default, users can create security groups, but admins can restrict this, in which case "you need at least the Groups Administrator role". — [Quickstart: Bicep with Microsoft Graph resources](https://learn.microsoft.com/graph/templates/bicep/quickstart-create-bicep-interactive-mode)
- Role assignments that carry the repo's ABAC condition are expressible in azurerm: `azurerm_role_assignment` supports `condition` and `condition_version` (`1.0` or `2.0`). The docs include an "ABAC Condition" example that assigns **Role Based Access Control Administrator** with `condition_version = "2.0"`. They also note `principal_type` must be set explicitly when the creating principal is constrained by ABAC rules that filter on PrincipalType. — [azurerm_role_assignment docs](https://github.com/hashicorp/terraform-provider-azurerm/blob/main/website/docs/r/role_assignment.html.markdown)

### Inferences
- An admin-run bootstrap authenticated as a user (az CLI) needs Groups Administrator, or higher, for the SQL-admin groups. That's the same Entra privilege the PowerShell script effectively needs today, so moving to Terraform adds no new Entra privilege.
- Setting `owners` explicitly (for example, a platform admin group) avoids the default "sole owner = whoever ran apply". That default would otherwise tie group management to one admin.
- Set `prevent_duplicate_names = true` so a re-created state doesn't silently make a second `andes-...-sqladmins` group.

### Gaps
- I didn't fetch the `azuread_group_member` resource page. If membership is managed separately from `members` on the group, check that page's permission list; for service principals it's likely `GroupMember.ReadWrite.All`, but I didn't verify this.

## Q3. Does Microsoft's ALZ IaC accelerator / accelerator-bootstrap-modules already implement this pattern? What does it create, how does it handle the state chicken-and-egg, and is it usable for an application landing zone?

### Takeaway
Yes, for the platform landing zone. The ALZ accelerator's bootstrap is a Terraform module (azurerm + azapi + microsoft/azuredevops, driven by the `ALZ` PowerShell module's `Deploy-Accelerator`). It creates state storage, separate plan and apply UAMIs, WIF service connections whose exported issuer/subject feed the UAMIs' federated credentials in one apply, ADO environments, variable groups, approvals, exclusive-lock and required-template checks, and pipelines. This is direct, Microsoft-authored confirmation of your claim. It isn't a drop-in for an application landing zone, though. It targets management-group-scoped platform deployment, it handles a single plan/apply pair rather than an environment map, it requires a PAT, and its own bootstrap state is local with "one-time operation" semantics. Microsoft's application-landing-zone tooling (lz-vending, now AVM sub-vending) creates UAMIs with federated credentials but no Azure DevOps objects.

### Cited Findings
**What it is and how it runs**
- "Welcome to the Azure landing zone IaC Accelerator for Bicep and Terraform!" The Azure Verified Modules for the Platform landing zone provide "an opinionated approach for deploying and managing the core platform capabilities". It "uses the ALZ PowerShell module to gather required user input" and applies a Terraform module to configure the bootstrap environment. Even for Bicep, "the accelerator uses Terraform to bootstrap the environment only." — [ALZ IaC Accelerator](https://azure.github.io/Azure-Landing-Zones/accelerator/)
- Run with `Deploy-Accelerator`, whose interactive wizard "only completes the bootstrap configuration file (`inputs.yaml`)". — [Phase 2 Bootstrap](https://azure.github.io/Azure-Landing-Zones/accelerator/2_bootstrap/)

### Inferences
- The ALZ bootstrap is the strongest available primary evidence for the recommendation. It's Microsoft's Terraform, using the exact `serviceendpoint → issuer/subject → federated credential` chain, maintained against a recent provider.
- Its state strategy differs from yours. ALZ keeps bootstrap state local and treats the bootstrap as one-time, while the repo's bootstrap recurs: one map entry per environment, possibly run by different admins. Local state on one laptop is the wrong fit for that, so keeping `New-TfStateBackend.ps1` and storing the bootstrap's own state remotely is the better choice here. ALZ's "create the backend inside the bootstrap, keep bootstrap state local" pattern works only because it never expects re-runs.
- It isn't directly reusable for this repo. It assumes management-group scope (Owner at the intermediate root), one plan/apply pair rather than per-environment pairs, Azure Repos (it creates repos and pushes a starter module; this repo is on GitHub), and a PAT. Its `modules/azure_devops` and `modules/azure` folders are, however, a good reference implementation to copy patterns from: checks on service connections, required-template check, exclusive lock, approver group, and separate plan (Reader) / apply identities.
- Design ideas worth adopting from ALZ:
  1. Separate plan and apply identities per environment, with read-only RBAC for plan, so PR plans run without write rights.
  2. `azuredevops_check_required_template` on the apply connection, so only the repo's `pipelines/templates` can use it.
  3. `azuredevops_check_exclusive_lock` to serialize applies.
  4. An `azuredevops_group` of approvers instead of individual users.
- The AVM sub-vending module could cover the Azure half (UAMIs, FICs via `federated_credentials_advanced`, role assignments) for app landing zones. The ADO service connection still has to exist first to supply the subject, so you'd end up composing it with `azuredevops_serviceendpoint_azurerm` anyway. For a single-subscription app like Andes, plain azurerm resources are simpler.

### Gaps
- No ALZ page explicitly states where the bootstrap state file lives. "Local, in the accelerator output folder" is inferred from the missing backend block plus the cleanup FAQ's dependence on the folder structure.
- I didn't verify whether `modules/azure_devops/pipeline.tf` uses `azuredevops_pipeline_authorization` or `azuredevops_resource_authorization` to pre-authorize pipelines on connections, environments and variable groups.
- I didn't check the AVM sub-vending successor's current registry name and version beyond the archive notice.

## Q4. Trade-offs: Terraform-based bootstrap vs PowerShell scripts (state location, who runs it, privileges, risk of an admin-level state file)

### Takeaway
A Terraform bootstrap gives you declarative drift detection, same-apply WIF wiring, and "add an environment = add a map entry", at the cost of a privileged state file and one more root module to run by hand. Keep the bootstrap state in the existing state storage account, in a separate container that only admins can reach. Run it as a human admin with az CLI (no PAT, no stored secret). With WIF and no secret variables, the state holds identifiers, not credentials, but write access to it must still be treated as privileged.

### Cited Findings
- "If you add secret values directly to your configuration, Terraform stores those secrets in its state and plan files." "Terraform stores your state in a plaintext file". The recommendations are to store state remotely, encrypt it at rest, use access controls, and keep audit logs. Ephemeral values (Terraform ≥ 1.10) and write-only arguments (≥ 1.11) are kept out of state. — [Terraform: Manage sensitive data](https://developer.hashicorp.com/terraform/language/manage-sensitive-data)
- Microsoft's automation guide lists the privileges needed to automate WIF service connections: *User Access Administrator* or *Role Based Access Control Administrator* (or higher) to create role assignments, plus Entra rights to create an app registration, or a managed identity instead. — [Automate ARM WIF service connections](https://learn.microsoft.com/azure/devops/pipelines/release/automate-service-connections?view=azure-devops)
- Entra group creation needs Groups Administrator, or higher, for a user principal (Q2). Adding app identities to an ADO organization needs Project Collection Administrators. Creating service connections needs the Creator/Administrator service-connection role. — [azuread_group](https://github.com/hashicorp/terraform-provider-azuread/blob/main/docs/resources/group.md); [ADO SP/MI](https://learn.microsoft.com/azure/devops/integrate/get-started/authentication/service-principal-managed-identity?view=azure-devops); [ADO Entra service connection prerequisites](https://learn.microsoft.com/azure/devops/pipelines/library/add-devops-entra-service-connection?view=azure-devops)
- Microsoft's own bootstrap is run by a human with a short-lived PAT ("Choose tomorrows date") and treated as one-time. — [ALZ ADO prerequisites](https://azure.github.io/Azure-Landing-Zones/accelerator/1_prerequisites/azuredevops/); [Upgrade FAQ](https://azure.github.io/Azure-Landing-Zones/accelerator/faq/upgrade/)
- A UAMI has a limit of 20 federated identity credentials. — [Learn: flexible federated identity credentials](https://learn.microsoft.com/uk-ua/entra/workload-id/workload-identities-flexible-federated-identity-credentials)

### Inferences
- **Where bootstrap state lives:** put it in the `New-TfStateBackend.ps1` storage account, in a dedicated container (for example `bootstrap`), with Entra-only data access. Grant Storage Blob Data Contributor on that container only to the admin group, and never to any pipeline identity. Today each environment's pipeline identity holds Storage Blob Data Contributor on its own state container, and the ABAC-conditioned RBAC Administrator role lets it assign roles. If a pipeline identity could write the bootstrap state, it could alter what the next admin apply does to privileged assignments (an indirect escalation). Keep shared keys disabled, per the repo convention, and enable blob versioning or soft delete for recovery.
- **What's in that state:** UAMI client and principal IDs, group object IDs, role assignment IDs including the ABAC condition text, the service connection ID, and the issuer/subject. With WIF and no secret variables, there are no credentials. Treat it as sensitive anyway, because it maps the privilege topology and is the input to an Owner-level apply.
- **Who runs it:** a human admin with `az login`. The azuredevops provider defaults to `use_cli = true` and azurerm/azuread can use the CLI too, so there's no PAT or stored secret. Running it from a pipeline would need an identity with Owner-equivalent plus Groups Administrator plus Project Collection Admin rights. That's a standing super-identity, and the repo deliberately avoids one ("The pipeline can't run these, by design").
- **Privileges for the runner:**
  - Owner, or User Access Administrator / RBAC Administrator plus Contributor, at subscription scope (the bootstrap creates RGs and role assignments, including RBAC Administrator with a condition).
  - Groups Administrator in Entra.
  - In Azure DevOps: Project Administrator plus the Endpoint Administrator/Creator role, and Project Collection Administrator if it creates projects or adds identities.

  These are the same privileges the current scripts plus manual steps already need, concentrated in one run.
- **Benefits over PowerShell:**
  1. The two-pass, copy-paste issuer/subject step goes away.
  2. `terraform plan` shows drift, such as a portal-converted issuer, a deleted FIC, or a changed approval.
  3. ADO objects that are hand-made today (variable groups, environments, approvals, pipeline permissions) become code.
  4. Removing an environment is declarative.
  5. The ABAC role list in `-AssignableRoleNames` can be one Terraform variable shared with the ABAC condition. The repo convention that "every Azure RBAC role Terraform assigns must be in `-AssignableRoleNames`" would then be enforced in code, not by memory.
- **Costs and risks:**
  1. One more root module and state to protect.
  2. Two kinds of provider churn: the azuredevops provider (issuer migration, issue #1573) and azurerm major versions, e.g. FIC argument changes in 5.x.
  3. `terraform destroy` or a bad refactor (missing `moved` blocks) can delete identities, groups and service connections that live environments depend on. Use `prevent_destroy` lifecycle rules on identities, groups and service connections.
  4. Graph replication delays between creating a group or UAMI and assigning roles. Set `principal_type` (azurerm docs note it's required under ABAC PrincipalType filters) and be ready to retry.
- **Keep PowerShell for the state backend:** this is consistent with common practice. Something has to exist before Terraform can use a remote backend. The alternative is ALZ's local-state, one-time approach, which doesn't fit a recurring bootstrap.

### Gaps
- I found no Microsoft guidance specific to "where should an application team's bootstrap state live"; the recommendation above is reasoning from Terraform's general guidance and the repo's ABAC design.

## Q5. Alternatives: azd pipeline config, `az devops` CLI scripting, Bicep for bootstrap, GitHub Actions instead of Azure DevOps

### Takeaway
- **azd:** a poor fit. It requires a PAT, targets Azure Repos for Azure Pipelines, and falls back to client secrets for Terraform projects.
- **az devops CLI:** Microsoft's documented scripting path. It can also remove the two-pass flow if you'd rather stay imperative.
- **Bicep:** can now create Entra groups and FICs (Graph Bicep is GA since July 2025), but has no Azure DevOps resources.
- **GitHub Actions:** the most structural simplification, since the code is already on GitHub. It removes service connections and the ADO bootstrap entirely, but it's a pipeline migration, not a bootstrap change.

### Cited Findings
- **azd:** For Azure DevOps (`--provider azdo`), "OIDC (federated) credentials are the default. `azd pipeline config` creates a workload identity federation service connection and the matching federated credential on the app registration". For Terraform, "If you don't define `--auth-type`, the command falls back to `client-credentials`… If `--auth-type` is explicitly set to `federated`, it will result in an error." — [azd tooling FAQ](https://learn.microsoft.com/azure/developer/azure-developer-cli/tooling-environment-faq#pipeline-configuration)
- azd for Azure Pipelines "Works with repositories hosted in Azure Pipelines", "Requires a Personal Access Token (PAT) with specific scopes", and sets up a service principal. — [Explore azd support for CI/CD pipelines](https://learn.microsoft.com/azure/developer/azure-developer-cli/configure-devops-pipeline); PAT scopes: [azd Azure Pipelines](https://learn.microsoft.com/azure/developer/azure-developer-cli/pipeline-azure-pipelines)
- **az devops CLI:** Microsoft's documented automation order is: create the identity (`az identity create`) → create the service connection (`az devops service-endpoint create` with a JSON config, `creationMode: Manual`, scheme `WorkloadIdentityFederation`), which returns `workloadIdentityFederationIssuer/Subject` → `az identity federated-credential create` → `az role assignment create`. — [Automate ARM WIF service connections](https://learn.microsoft.com/azure/devops/pipelines/release/automate-service-connections?view=azure-devops)
- **Bicep:** "Bicep templates for Microsoft Graph resources is now generally available and supported in production environments". Supported types include Applications, App role assignments, Federated identity credentials, Groups, OAuth2 permission grants, Service principals and Users (July 2025). — [Microsoft Graph what's new (July 2025)](https://learn.microsoft.com/graph/whats-new-earlier#july-2025-new-and-generally-available); [Graph Bicep quickstart](https://learn.microsoft.com/graph/templates/bicep/quickstart-create-bicep-interactive-mode)
- **GitHub Actions:** to use `azure/login` with OIDC, "configure a federated identity credential on a Microsoft Entra application or a user-assigned managed identity", one that trusts tokens GitHub issues to your repository. — [Use the Azure Login action with OpenID Connect](https://learn.microsoft.com/azure/developer/github/connect-from-azure-openid-connect)
- The ALZ accelerator supports GitHub as a first-class bootstrap target: environments, an apply approval team, a "customized OIDC token subject", and action variables (not secrets). — [ALZ IaC Accelerator](https://azure.github.io/Azure-Landing-Zones/accelerator/)
- The lz-vending/AVM sub-vending module has a native `federated_credentials_github` input for UAMIs. — [lz-vending README](https://github.com/Azure/terraform-azurerm-lz-vending)

### Inferences
- **azd:** fits greenfield app templates where azd owns both infra and deploy and the repo lives in Azure Repos or GitHub. It doesn't fit here: Terraform + federated is unsupported (client secret instead, which violates the no-secrets rule), it needs a PAT, it creates an app registration rather than using the existing UAMI pattern, and there's no Entra SQL-admin group, ABAC role, or environment approvals.
- **`az devops` + Az PowerShell:** fits if the team wants to stay imperative and avoid a privileged state file. `New-AppEnvironment.ps1` could become single-pass by calling `az devops service-endpoint create` (or the REST API) right after creating the UAMI, then reading `authorization.parameters.workloadIdentityFederationIssuer/Subject` to create the FIC. That removes the two-pass flow without Terraform, though you still won't get drift detection or declarative ADO environments, approvals and variable groups.
- **Bicep (+ Graph extension) + az devops:** fits only if the organization standardizes on Bicep. It can now declare the RG, UAMI, FIC, role assignments (with conditions, via ARM) and Entra groups. The ADO half would remain scripts, and the WIF ordering (service connection before FIC) would span two tools, recreating a version of the two-pass problem.
- **GitHub Actions instead of Azure DevOps:** fits if the team can move pipelines. Since the repo is on GitHub, the FIC subject becomes predictable (`repo:<org>/<repo>:environment:<env>`; see the GitHub OIDC docs for exact formats), so there's no service connection object and no chicken-and-egg. The bootstrap shrinks to azurerm + azuread, plus optionally the `integrations/github` provider for environments and protection rules. GitHub Environments supply required reviewers. The trade-offs:
  1. A pipeline rewrite, with `pipelines/*.yml` moving to `.github/workflows`.
  2. Different approval and audit semantics.
  3. Hardening work on the workflows: pinning, least-privilege `GITHUB_TOKEN`, and avoiding `pull_request_target`.

  This is a bigger decision than the bootstrap, so treat it as a separate ADR.
- **Microsoft-provided tooling that "already does this":** the ALZ accelerator does it for platform landing zones only. For an application environment set like Andes (dev → qa/uat/staging/prod in one or a few subscriptions, GitHub repo, ADO pipelines), I found no Microsoft tool that does it end to end. A small custom Terraform root module modelled on `accelerator-bootstrap-modules/modules/{azure,azure_devops}` is the closest fit.

### Gaps
- I didn't verify the exact current GitHub OIDC subject formats (environment vs branch vs custom subject templates) or the `integrations/github` provider's environment and reviewer resources; check them in GitHub docs if that route is considered.
- I didn't check whether azd added Terraform federated support after the Learn page's last update.

## Q6. Verdict on the recommendation and corrections to the claims

### Takeaway
**The evidence confirms the recommendation, with three corrections.**
1. The "private preview" note is stale, as you suspected (WIF has been GA since Sprint 234, early 2024). But the doc's issuer/subject *formats* are also stale: new connections use the Microsoft Entra issuer and a GUID-based subject, and the old issuer retires on 1 July 2027. That makes consuming the provider's computed outputs mandatory.
2. The provider's example targets older azurerm and has a quoting bug. With azurerm 5.x, use `user_assigned_identity_id` on `azurerm_federated_identity_credential`.
3. Microsoft tooling already implements this exact pattern (the ALZ accelerator bootstrap), but only for the platform landing zone, with local one-time state and a PAT. Model on it rather than adopt it, and keep your remote-state approach because your bootstrap recurs.

### Cited Findings
- Same-apply wiring is documented by the provider ([serviceendpoint_azurerm](https://github.com/microsoft/terraform-provider-azuredevops/blob/main/website/docs/r/serviceendpoint_azurerm.html.markdown)) and used by Microsoft's ALZ bootstrap ([outputs.tf](https://github.com/Azure/accelerator-bootstrap-modules/blob/main/modules/azure_devops/outputs.tf), [locals.tf](https://github.com/Azure/accelerator-bootstrap-modules/blob/main/alz/azuredevops/locals.tf)). Microsoft's automation guide gives the dependency order: service connection → issuer/subject → FIC ([automate-service-connections](https://learn.microsoft.com/azure/devops/pipelines/release/automate-service-connections?view=azure-devops)).
- WIF GA: [Sprint 234 release notes](https://learn.microsoft.com/azure/devops/release-notes/2024/sprint-234-update). Entra issuer default and vstoken retirement on 2027-07-01: [Connect to Azure](https://learn.microsoft.com/azure/devops/pipelines/library/connect-to-azure?view=azure-devops); formats: [Troubleshoot WIF](https://learn.microsoft.com/azure/devops/pipelines/release/troubleshoot-workload-identity?view=azure-devops).
- Provider gaps are still open: in-place issuer conversion ([#1573](https://github.com/microsoft/terraform-provider-azuredevops/issues/1573), Jul 2026) and the Entra-issuer breaking change ([#1361](https://github.com/microsoft/terraform-provider-azuredevops/issues/1361)).
- azurerm FIC arguments: [azurerm federated_identity_credential](https://github.com/hashicorp/terraform-provider-azurerm/blob/main/website/docs/r/federated_identity_credential.html.markdown).
- ADO environments, all check types, pipeline/resource authorization, variable groups (including Key Vault-linked) and GitHub-repo build definitions all exist as provider resources: [docs/r](https://github.com/microsoft/terraform-provider-azuredevops/tree/main/website/docs/r), [variable_group](https://github.com/microsoft/terraform-provider-azuredevops/blob/main/website/docs/r/variable_group.html.markdown), [build_definition](https://github.com/microsoft/terraform-provider-azuredevops/blob/main/website/docs/r/build_definition.html.markdown).

### Inferences
- Recommended shape:
  - One admin-run root module (for example `bootstrap/terraform/`) with `for_each` over `var.environments`, creating per environment:
    1. The RG.
    2. Plan and apply UAMIs, or one UAMI as today.
    3. The state container.
    4. Role assignments, including RBAC Administrator with the ABAC `condition`, driven by the same role list.
    5. The Entra SQL-admin group (explicit owners, `prevent_duplicate_names`).
    6. The WIF service connection(s).
    7. FICs from the exported issuer/subject.
    8. The ADO environment.
    9. Approval, exclusive-lock and required-template checks.
    10. A non-secret variable group.
    11. `azuredevops_pipeline_authorization` for the existing pipeline.
  - Authenticate all three providers via `az login` (no PAT).
  - Store the module's state remotely in a separate, admin-only container of the PowerShell-created backend.
  - Add `prevent_destroy` on identities, groups and connections.
- Since existing environments already have hand-made objects (service connection, variable groups, environments), plan for `import` blocks. The provider supports import for checks (1.16.0) and pipeline authorization (1.14.0), but variable groups containing secret values can't be imported.
- Track issue #1573 and convert any vstoken-issuer connections before July 2027. Terraform will repair the FIC when the subject changes.

### Gaps
- The verdict assumes the Azure DevOps organization behaves as the current Learn docs describe (Entra issuer for new connections). Microsoft rolled the Entra issuer back for "most" organizations in April 2025 ([#1361](https://github.com/microsoft/terraform-provider-azuredevops/issues/1361)) and the current Learn page says Entra is the default. Which issuer this specific org gets can only be confirmed by creating a test connection. The Terraform design works either way.
