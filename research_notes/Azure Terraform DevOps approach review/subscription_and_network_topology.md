# Subscription and network topology: Microsoft guidance check (as of October 2026)

Scope: whether Microsoft guidance current in October 2026 supports (a) giving prod its own subscription while non-prod environments share one, and (b) using VNet integration, service endpoints and default-deny firewalls now, with private endpoints as the production option. The workload is a Windows App Service API and SPA, plus Key Vault, Storage, SQL and Cosmos DB.

Repo facts checked against the code (not taken from docs alone):
- Key Vault, Storage, SQL and Cosmos keep public network access enabled. Their firewalls default to Deny and allow only the API subnet plus an IP allowlist (`terraform/key_vault.tf`, `storage.tf`, `sql.tf`, `cosmos.tf`).
- The API sets `vnet_route_all_enabled = true` and `virtual_network_subnet_id` (`terraform/app_service.tf`).
- The pipeline runs on the Microsoft-hosted `ubuntu-24.04` image (`pipelines/infra-pipeline.yml`).
- The SQL grant step opens a temporary SQL firewall rule for the runner's public IP: `-AddRunnerFirewallRule` in `scripts/Grant-SqlManagedIdentityAccess.ps1`, called from `pipelines/templates/terraform-environment.yml`.
- The tfstate storage account is left network-open by default "because Microsoft-hosted Azure DevOps agents use dynamic IPs" (`bootstrap/New-TfStateBackend.ps1`).
- Dev uses `vnet_address_space = "10.10.0.0/24"` and `app_service_plan_sku = "B1"` (`terraform/environments/dev/terraform.tfvars`). `docs/infrastructure.md` plans qa `10.11.0.0/24`, uat `10.12.0.0/24`, staging `10.13.0.0/24` and prod `10.14.0.0/24`.

## Q1. CAF / Azure landing zone guidance on separating production and non-production (subscriptions vs resource groups)

### Takeaway
**Verdict on (a): confirms.** Current CAF guidance says to put production, non-production and sandbox in separate subscriptions. Its "ideal" is one subscription per environment, but its small-organization starting point is exactly "one production, one nonproduction, one sandbox subscription". CAF explicitly allows several environments to share one subscription when the same team operates them under the same policies, which fits non-prod here. Separate resource groups for non-prod environments inside a shared non-prod subscription are therefore an accepted pattern. Keeping prod in that shared subscription is what CAF warns against.

### Cited Findings
- The CAF Azure setup guide for initial subscriptions says: "**Avoid placing multiple workload environments in the same subscription. Create separate subscriptions for production, nonproduction, and sandbox environments.** Each environment requires distinct governance policies and access controls. This separation protects production workloads, supports innovation, and simplifies cost tracking, access control, and policy enforcement." — [CAF: Create and scale Azure subscriptions](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/azure-setup-guide/initial-subscriptions#start-with-subscription-policies)
- The same page gives a minimum starting structure: "**Start with three core subscriptions** to establish proper boundaries. Create one production subscription for live workloads, one nonproduction subscription for development and testing, and one sandbox subscription for experimentation and learning. This structure provides essential separation while keeping management overhead low and costs predictable." It also says to use Azure Dev/Test pricing for non-prod, because those benefits "help small organizations maximize their cloud investment while maintaining proper environment separation." — [CAF: Create and scale Azure subscriptions](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/azure-setup-guide/initial-subscriptions#start-with-subscription-policies)
- Subscription democratization (an ALZ design principle) says: "**Use subscriptions to separate application environments.** Subscriptions should also be used to control and segregate environments across the software development lifecycle (SDLC), such as development, testing, and production. This separation improves governance, reduces risk, and supports consistent workload management." It also says "Use subscriptions as units of management." — [ALZ design principles: Subscription democratization](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-principles#subscription-democratization)
- From application environments in ALZ: "Ideally, each application environment should have its own subscription. This method provides security and policy controls that keep the environments isolated. It contains potential problems to one environment." — [Manage application development environments in Azure landing zones](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- That page also states when sharing a subscription is acceptable: "Use a single subscription for multiple application environments if: The environments can't be isolated in their own subscriptions. The environments have the same teams assigned to functional roles, such as network operators. The environments can use the same policies." It adds: "We recommend that workload owners work with cloud platform teams to determine if a single subscription for multiple environments is needed." — [same page](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- **Counterpoint, specific to App Service**, on the same page: deployment slots "can only be used with the app that's on the App Service plan, which can only live within a single subscription. If the platform operators mandate that the application owners use separate subscriptions for development, testing, and production environments, the application deployment lifecycle might be more difficult to manage. For this example, the best option is a single subscription for the application or service workload. Application owners can use Azure role-based access control (RBAC) with PIM at the resource group level for increased security." — [same page, "Scenario: Azure App Service"](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- CAF advises against environment-specific management groups or policies: "SDLC environments shouldn't have different policies, so we don't recommend separate management groups." Its worked example is a storage account that uses private endpoints and firewall policy in prod but not in dev, so "the deployment fails because of the enforced policy" when the app is promoted. — [same page, "Environment-based management group challenges"](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- In a single subscription, environment controls are weaker: "Unlike policies and controls at the management group level, subscription-based policies and tags can be changed by individuals with elevated permissions to the subscription. Administrators with appropriate roles can bypass these controls by excluding policies, modifying policies, or changing the tags on resources." — [same page, Warning](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- From ALZ identity guidance: "Maintain separate security configurations for different environments of the same application, such as dev/test and production. Create separate groups and role assignments for each environment. **Don't share managed identities or service principals across environments. Treat each environment as a separate landing zone.**" — [Landing zone identity and access management](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/identity-access-landing-zones#design-recommendations)
- CAF environments guidance says to "Use separated Service Principals for test and production purposes to protect your environments." — [CAF: Environments](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/considerations/environments#design-considerations)
- In the ALZ conceptual architecture: "A workload landing zone contains all the environments required to support that workload, such as development, test, and production. Each environment consists of one or more Azure subscriptions based on workload requirements, team ownership boundaries, or Azure subscription limits." — [What is an Azure landing zone?](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/#workload-landing-zone)
- CAF's ISV guidance warns about starting with a single subscription: "Although this is technically possible, you'll face challenges later on when you need to move resources between subscriptions and find that not all resource types can be moved." — [ISV considerations for an Azure landing zone](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/isv-landing-zone)
- An App Service-specific limitation makes later moves harder: "You can't change the subscription of an app or a plan while there's an app that's using virtual network integration." — [App Service VNet integration: Limitations](https://learn.microsoft.com/azure/app-service/overview-vnet-integration#limitations)
- The WAF mission-critical guidance says: "**Environment boundaries.** Deploy production, development, and test environments into separate subscriptions. This practice ensures that lower environments don't contribute toward scale limits. It also reduces the risk of lower-environment updates polluting production by providing a clear management and identity boundary." — [Mission-critical deployment and testing](https://learn.microsoft.com/azure/well-architected/mission-critical/mission-critical-deployment-testing#subscription-scoped-deployment)

### Inferences
- The "prod alone, non-prod shared" split matches the CAF "three core subscriptions" minimum. The shared non-prod subscription (dev, qa, uat, staging) meets CAF's three conditions for sharing: one team, the same functional roles, and the same policies. Resource-group isolation is acceptable for non-prod but not for prod.
- The App Service slot counterpoint doesn't apply to this repo. Each environment already has its own App Service plan (`andes-asp-<env>`), so slots can't span environments even in one subscription. A prod staging slot lives on the prod plan in the prod subscription either way. The CAF argument targets teams that use slots as their dev/test/prod environments, which this design doesn't do.
- The current design already follows the identity guidance (per-environment pipeline identity, API identity and SQL admin group). However, every environment's pipeline identity lives in `andes-rg-tfstate` in the shared subscription, and one tfstate account holds all environments' state containers. With a prod subscription, prod gets its own state backend and identity resource group (the bootstrap already runs "once per subscription"). That removes the remaining shared prod/non-prod blast radius: the subscription Owner, the state account and the identity RG.
- Because a VNet-integrated app or plan can't change subscription, and not all resource types can be moved, prod should be in its own subscription before it is first deployed. Moving it later means disconnecting VNet integration and re-creating or moving resources.
- CAF's "consistent policies across SDLC environments" guidance is a caution for the network design (see Q3). If prod alone uses private endpoints with public access disabled, the first environment that exercises that topology is prod.

### Gaps
- No CAF statement gives a team-size threshold below which resource-group-only isolation of prod is endorsed. CAF frames it by roles and policies, not headcount.
- The CAF "initial subscriptions" page carries no visible "last updated" date in the fetched content. It was retrieved live on 2026-10-10 and reflects current Learn content.

## Q2. Subscription limits/quotas, Azure Policy, budgets/cost management and RBAC reasons to split prod

### Takeaway
**Partially confirms.** Limits are not a driver at this workload's scale (980 resource groups and 5,000 role assignments per subscription). Policy, RBAC and budgets can all be scoped to a resource group. The real reasons to split prod are:
- The subscription Owner and subscription-scoped controls are a shared blast radius.
- Defender for Cloud plans are mostly enabled per subscription.
- Azure Dev/Test pricing requires a separate Dev/Test-offer subscription, which may not hold prod.
- CAF's policy-boundary and management-boundary principles.

### Cited Findings
- CAF: "Subscriptions serve as boundaries for scale, quota, cost, governance, security, and identity controls for Azure resources that are contained within them." Its subscription principles are **scale limits**, **management boundary** ("Various environments, such as development, test, and production environments, are often removed from a management perspective"), **policy boundary** ("Development environments have more relaxed policy requirements than production environments"), and **target network topology** ("You can't share virtual networks across subscriptions"). — [CAF: Subscription considerations and recommendations](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/resource-org-subscriptions)
- Platform limits: 980 resource groups per subscription — [Azure subscription and service limits: General limits](https://learn.microsoft.com/azure/azure-resource-manager/management/azure-subscription-service-limits#general-limits). 5,000 Azure role assignments per subscription, which "includes role assignments at the subscription, resource group, and resource scopes" and "is fixed and cannot be increased" — [Troubleshoot Azure RBAC limits](https://learn.microsoft.com/azure/role-based-access-control/troubleshoot-limits#symptom---no-more-role-assignments-can-be-created); [limits table](https://learn.microsoft.com/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-rbac-limits)
- Azure Policy: 200 policy or initiative assignments per scope, where for assignments "Scope means the management group, subscription, resource group, or individual resource". So policy can be assigned at resource-group scope. — [Azure Policy limits](https://learn.microsoft.com/azure/azure-resource-manager/management/azure-subscription-service-limits#azure-netapp-files)
- CAF says that in a shared subscription you can "Use policies that are applied at the subscription level instead of the management group level... You can also assign policies to or exclude them from specific resource groups." It warns that subscription-level policies can be bypassed by subscription admins (quoted in Q1). — [Manage application development environments](https://learn.microsoft.com/azure/cloud-adoption-framework/ready/landing-zone/design-area/management-application-environments)
- Budgets work at management group, subscription **and resource group** scopes: "If you want to create a budget for a resource group, ensure that you navigate to one first." — [Tutorial: Create and manage budgets](https://learn.microsoft.com/azure/cost-management-billing/costs/tutorial-acm-create-budgets#prerequisites)
- Defender for Cloud: "You can enable Microsoft Defender for Storage accounts, Microsoft Defender for SQL, and Microsoft Defender for open-source relational databases at either the subscription level or resource level." Also, "When you enable Defender plans on an entire Azure subscription, the protections apply to all other resources in the subscription." — [Connect your Azure subscriptions](https://learn.microsoft.com/azure/defender-for-cloud/connect-azure-subscription#enable-all-paid-plans-on-your-subscription). Microsoft recommends enabling Defender for SQL "at the subscription level so that new resources are automatically protected" — [Microsoft Defender for SQL](https://learn.microsoft.com/azure/azure-sql/database/azure-defender-for-sql?view=azuresql#enable-microsoft-defender-for-sql). Defender for App Service is paid "per App Service plan" and can be toggled on the plan — [Disable Defender for Cloud plans](https://learn.microsoft.com/azure/defender-for-cloud/disable-plans#check-resource-level-settings)
- Dev/Test pricing comes from separate subscription offers: Pay-As-You-Go Dev/Test (0023P) and Enterprise Dev/Test (0148P). Both require Visual Studio subscriptions. "If you're running mission-critical services like customer-facing applications, don't use a Dev/Test subscription. Dev/Test subscriptions don't carry a financially backed SLA." — [Azure Dev/Test reliability management](https://learn.microsoft.com/azure/devtest/offer/how-to-manage-reliability-performance). Azure Dev/Test "provides discounted pricing for Azure services - such as virtual machines, Azure SQL Database, and App Service - to support non-production workloads." — [What is the Azure Dev/Test offer?](https://learn.microsoft.com/azure/devtest/offer/overview-what-is-devtest-offer-visual-studio)
- On RBAC: "If you must assign a privileged administrator role, use a narrow scope, such as resource group or resource, instead of a broader scope, such as management group or subscription." — [Best practices for Azure RBAC](https://learn.microsoft.com/azure/role-based-access-control/best-practices#limit-privileged-administrator-role-assignments)

### Inferences
- For a workload this small, subscription limits are irrelevant as a reason to split. Budgets and resource-group-scoped policy and RBAC also work in a shared subscription, and the repo already scopes budgets and RBAC per resource group.
- The decisive factors are these:
  1. The bootstrap admin is Owner on the whole subscription, so in one subscription "Owner" means Owner of prod and of non-prod. A split lets non-prod Owner or Contributor go to more people without touching prod.
  2. The production checklist in `docs/infrastructure.md` says to enable Defender for SQL, Storage, Key Vault and App Service. Enabling these at subscription level, which Microsoft recommends, would also cover and bill non-prod in a shared subscription; the alternative is per-resource toggles. Defender for Key Vault isn't listed as a resource-level option, so it is likely subscription-only (inferred, not confirmed).
  3. Dev/Test pricing on App Service and SQL is only available if non-prod sits in a Dev/Test-offer subscription, which by definition can't host prod.
  4. Subscription-level policy, Service Health and activity-log alerts can then differ for prod without tag-based scoping, which CAF warns can be bypassed.
- The repo's ABAC-constrained pipeline identity, scoped to one resource group, is a strong compensating control while everything shares one subscription. It doesn't protect against subscription-level actors (Owners, subscription-scoped policy edits).

### Gaps
- I didn't confirm whether Defender for Key Vault can be enabled per resource in October 2026; the Learn page lists only Storage, SQL and OSS relational databases as resource-level.
- I didn't find exact current Dev/Test discount percentages for App Service and SQL Basic; Microsoft's docs say only "discounted".

## Q3. Service endpoints vs private endpoints for App Service to Key Vault, Storage, SQL and Cosmos DB

### Takeaway
**Verdict on (b): confirms for dev and test, partially confirms for prod.** Microsoft recommends Private Link in general and for production. Its current networking design guide explicitly maps "dev/test, low data sensitivity" to public endpoints with a service firewall, and "simple VNet restriction, low exfiltration risk" to service endpoints, so the current design is within guidance for non-prod. I found no deprecation of (basic) service endpoints. Microsoft is adding a paid "standard service endpoint" (preview) for exactly the four services in this design. For prod, calling private endpoints "an option" is weaker than Microsoft's wording ("Production workloads… Preferred over Service Endpoints for new designs"; MCSB NS-2 is "Must have"). Prod should be designed for private endpoints with public access disabled, not merely "consider" them.

### Cited Findings
- From the Azure networking design guide, "Private access to Azure PaaS services" (current Learn content), under "When to use which approach":
  - "Dev/test, low data sensitivity | **Public endpoint with service firewall** | Simplest setup. Restrict access by IP allow listing. No extra cost or DNS changes."
  - "Simple VNet restriction, low exfiltration risk | **Service Endpoints** | Free. Quick to enable. Appropriate when you don't need resource-level access scoping."
  - "Production workloads, sensitive data, compliance | **Private Endpoints** | Strongest exfiltration protection."

  The services table rates Private Endpoint as for "Production workloads. Sensitive data. Regulatory compliance. Data exfiltration prevention. **Preferred over Service Endpoints for new designs.**" — [Private access to Azure PaaS services](https://learn.microsoft.com/azure/networking/design-guide/private-platform-as-a-service)
- The same guide on exfiltration: "Service Endpoints… restrict access at the VNet level but apply to all instances of a service type… This gap makes Service Endpoints insufficient for environments where data exfiltration is a compliance concern." It also says: "After you configure a Private Endpoint for a PaaS service, turn off public network access on that service. If public access remains enabled, traffic can still reach the service over the internet." — [same page](https://learn.microsoft.com/azure/networking/design-guide/private-platform-as-a-service)
- From the VNet integration comparison: "**Microsoft recommends using Azure Private Link.** Private Link offers better capabilities for privately accessing PaaS from on-premises, provides built-in data-exfiltration protection, and maps services to private IPs in your own network." The comparison table says service endpoints are "Simple to set up with less management overhead", have no cost or SLA impact, and the "Service can disable its public IP address: No". — [Integrate Azure services with virtual networks](https://learn.microsoft.com/azure/virtual-network/vnet-integration-for-azure-services#compare-private-endpoints-and-service-endpoints)
- Microsoft cloud security benchmark v2, NS-2: deploy private endpoints, configure private DNS zones, then "Disable public access". The note says: "Certain Azure services may also allow private communication through the service endpoint feature, **though Azure Private Link is recommended** for secure and private access." NS-2.3 also covers service-native firewalls ("Define IP-based or VNet-based rules"; "Disable public access when possible"). The criticality level is "**Must have**". — [MCSB v2: Network Security NS-2](https://learn.microsoft.com/security/benchmark/azure/mcsb-v2-network-security#ns-2-secure-cloud-native-services-with-network-controls)
- Key Vault ranks its options "from most restricted to least restricted": (1) "Disable public network access and use Private Endpoints only"; (2) "Enable Key Vault Firewall: Limit access to public static IP addresses or your virtual networks." Both are presented as valid choices: "Pick the configuration that best suits your organization's use case." — [Secure your Azure Key Vault: Network security](https://learn.microsoft.com/azure/key-vault/general/secure-key-vault#network-security)
- Defender for Cloud has two Key Vault recommendations, both Medium severity: "Azure Key Vault should have firewall enabled or public network access disabled", which the current design satisfies, and "Azure Key Vaults should use private link", which it doesn't. — [Key Vault security recommendations](https://learn.microsoft.com/azure/defender-for-cloud/recommendations-reference-keyvault#azure-keyvault-recommendations)
- The App Service security baseline, NS-2: "Disable Public Network Access' using either service-level IP ACL filtering rules or private endpoints". — [Azure security baseline for App Service](https://learn.microsoft.com/security/benchmark/azure/baselines/app-service-security-baseline#network-security)
- The Azure Architecture Center baseline web app suggests built-in policies including "App Service should use virtual network integration" and "App Service should use Private Link to connect to PaaS services". — [Baseline highly available zone-redundant web application](https://learn.microsoft.com/azure/architecture/web-apps/app-service/architectures/baseline-zone-redundant#considerations)
- **Standard service endpoint (preview, new):** "addresses the scale limitations in basic service endpoints". It uses a public IP "network identifier" plus a network security perimeter. Supported services are exactly Storage, Key Vault, SQL Database and Cosmos DB. It is "currently in preview… not recommended for production workloads". The comparison table lists basic service endpoint pricing "Free" and standard "Paid". On pricing the page says "Standard Service Endpoint is available at no charge in July 2026. Billing is expected to begin after the preview announcement, currently targeted for August 2026" (stale wording on a page fetched in October 2026). — [What is a standard service endpoint?](https://learn.microsoft.com/azure/private-link/service-endpoint-standard-overview)
- Network security perimeter is generally available in all Azure public regions as a way to secure PaaS public endpoints. — [What is Azure Private Link?](https://learn.microsoft.com/azure/private-link/private-link-overview); see also [Azure Storage network security overview](https://learn.microsoft.com/azure/storage/common/storage-network-security-overview#public-endpoints)
- A search for a retirement announcement for VNet service endpoints returned nothing; the only results were unrelated 2026 retirements. — [web search results, e.g. Azure VPN Client for Linux retirement](https://learn.microsoft.com/en-my/azUre/virtual-wan/azure-vpn-client-linux-retirement)
- Private endpoint cost and complexity: a "Per-endpoint hourly charge plus data processing fee"; it "Requires DNS changes" (private DNS zones such as `privatelink.blob.core.windows.net`, `privatelink.database.windows.net`, `privatelink.vaultcore.azure.net`, `privatelink.documents.azure.com`). — [Private access to Azure PaaS services](https://learn.microsoft.com/azure/networking/design-guide/private-platform-as-a-service). Private endpoint is "available for Windows web apps and Linux web apps… hosted on Basic, Standard, Premium v2, Premium v3, and Isolated v2 App Service plans." — [Improved-security access to App Service web apps from an on-premises network](https://learn.microsoft.com/azure/architecture/web-apps/guides/networking/access-multitenant-web-app-from-on-premises#considerations)
- **Windows worker IP overlap, new in current docs (table dated "as of October 2026"):** "For Windows apps, an outbound connection through virtual network integration fails if the destination IP address matches an infrastructure IP address of the App Service worker… The destination can be a private endpoint, a virtual machine network interface, or another resource in your virtual network." For **B1, S1, P1**, the infrastructure ranges are `10.10.0.0/19`, `10.11.0.0/19`, `172.18.0.0/19` and `172.19.0.0/19`. For P0v3 they are `10.70.x/10.71.x` and `172.22.96.0/19`/`172.23.96.0/19`; P1v3 is listed at `10.70.0.0/19`/`10.71.0.0/19`. "These ranges describe current infrastructure allocations and can change." — [App Service VNet integration: Windows worker IP address overlap](https://learn.microsoft.com/azure/app-service/overview-vnet-integration#windows-worker-ip-address-overlap)

### Inferences
- Service endpoints with default-deny firewalls are inside Microsoft's own decision table for dev and test. Nothing indicates they are deprecated: Microsoft is building a paid "standard" tier on top of them for these exact four services. Basic service endpoints stay free and are still the documented way for VNet-integrated App Service to reach "service endpoint-secured services".
- For prod, Microsoft's wording is stronger than "an option": private endpoints are preferred for new designs and for production or sensitive data, and MCSB NS-2 is "Must have". The "Production checklist → Network: consider private endpoints" line in `docs/infrastructure.md` understates the guidance. A stronger stance would be: prod uses private endpoints with public network access disabled, unless a documented risk acceptance says otherwise.
- **Concrete risk found in this repo:** dev's VNet is `10.10.0.0/24`, and the doc plans qa at `10.11.0.0/24`. Both fall inside the Windows B1/S1/P1 worker infrastructure ranges (`10.10.0.0/19`, `10.11.0.0/19`). Today this is harmless, because service-endpoint traffic targets the services' public IPs. If private endpoints were added in those VNets, for example to rehearse the prod topology in a lower environment, Windows apps on B1, S1 or P1 could fail to connect. Planned uat (`10.12`), staging (`10.13`) and prod (`10.14`) don't overlap any listed range. That holds for the P0v3 tier recommended in the production checklist and for S1 or P1, though Microsoft says the ranges can change. Renumbering dev and qa away from `10.10.0.0/19` and `10.11.0.0/19` before any private-endpoint work would avoid this.
- Following CAF's "consistent policies across SDLC environments" principle (Q1), at least one pre-prod environment (staging is the natural one) should use the same private-endpoint and public-access-disabled topology as prod. Otherwise private DNS, agent line-of-sight and the SQL grant step are first exercised in prod.
- The `vnet_route_all_enabled` setting the repo uses maps to the legacy route-all switch. Current App Service docs recommend `outboundVnetRouting.allTraffic` instead, saying "The legacy `vnetRouteAllEnabled` site setting and `WEBSITE_VNET_ROUTE_ALL` app setting are still supported for backwards compatibility" ([Manage VNet integration routing](https://learn.microsoft.com/azure/app-service/configure-vnet-integration-routing)). The current setting works; the newer property is policy-auditable.

### Gaps
- I didn't verify whether the azurerm provider in use exposes `outboundVnetRouting.allTraffic`, or which App Service property `vnet_route_all_enabled` writes to; the terraform MCP server or registry would be needed.
- No Microsoft statement says service endpoints are "not recommended" for dev and test. The design guide's table is the clearest positive endorsement found.
- The standard service endpoint billing start date (August 2026 target) wasn't confirmed as having happened; the page wording is stale.

## Q4. Confirm the Storage firewall same-region limitation, and that Windows App Service on Basic supports regional VNet integration and route-all

### Takeaway
**Confirms both.** Azure Storage IP network rules have no effect on requests from the same Azure region, including Azure services. Microsoft says to use virtual network rules (or private endpoints), which is exactly why the design uses VNet integration and service endpoints. Regional VNet integration is supported on Basic (and higher) dedicated tiers at no extra charge. It works for Windows apps, and route-all is a supported configuration. One Windows-specific caveat applies (the worker IP overlap in Q3).

### Cited Findings
- From the Storage firewall restrictions: "You can't use IP network rules to restrict access to clients in the same Azure region as the storage account. **IP network rules have no effect on requests that originate from the same Azure region as the storage account.** Use Virtual network rules to allow same-region requests." Also: "You can't use IP network rules to restrict access to Azure services deployed in the same region as the storage account. Services deployed in the same region as the storage account use private Azure IP addresses for communication." — [Guidelines and limitations for the Azure Storage firewall](https://learn.microsoft.com/azure/storage/common/storage-network-security-limitations#restrictions-for-ip-network-rules)
- "If you enable a service endpoint for a subnet, traffic from that subnet won't use a public IP address to communicate with a storage account… As a result, IP network rules that permit traffic from those subnets no longer have an effect." — [Azure Storage firewall rules](https://learn.microsoft.com/azure/storage/common/storage-network-security#ip-network-rules)
- The same limitation appears in Azure DevOps docs: "Azure Storage IP firewall rules don't apply to requests that originate from the same Azure region as the storage account." — [Azure DevOps: Prepare for test run migration](https://learn.microsoft.com/azure/devops/migrate/migration-prepare-test-run?view=azure-devops#restrict-access-to-azure-devops-services-ips-only)
- A Microsoft Q&A answer (Microsoft support staff, not product docs) says the limitation applies to same-tenant, same-region traffic, and that cross-tenant traffic was observed to honor IP rules. — [Microsoft Q&A](https://learn.microsoft.com/answers/a/12284247). This is secondary and not reflected in the product docs.
- VNet integration "Requires a Basic, Standard, Premium, Premium v2, Premium v3, Premium v4, or Elastic Premium App Service pricing tier." It supports reaching "Service endpoint-secured services" and "Private endpoint-enabled services." "The virtual network integration feature has no extra charge for use beyond the App Service plan pricing tier charges." — [Integrate your app with an Azure virtual network](https://learn.microsoft.com/azure/app-service/overview-vnet-integration)
- On route-all: "When all traffic routing is enabled, all outbound traffic is sent into your virtual network. If all traffic routing isn't enabled, only private traffic (RFC1918) and service endpoints configured on the integration subnet is sent into the virtual network." — [same page](https://learn.microsoft.com/azure/app-service/overview-vnet-integration#how-virtual-network-integration-works). "We recommend that you use the `outboundVnetRouting.allTraffic` property to enable routing of all traffic… The legacy `vnetRouteAllEnabled` site setting and `WEBSITE_VNET_ROUTE_ALL` app setting are still supported for backwards compatibility." — [Manage App Service VNet integration routing](https://learn.microsoft.com/azure/app-service/configure-vnet-integration-routing)
- Windows-specific limitations: "Windows apps can't connect to a destination IP address that matches an App Service worker infrastructure IP address." Also: "Connectivity to global Azure Storage accounts might fail for VNet-integrated apps when virtual network Route All is enabled and the app doesn't use service endpoints, private endpoints, or User-Defined Routes" (the fix is to enable service endpoints, which this design does). — [VNet integration: Limitations](https://learn.microsoft.com/azure/app-service/overview-vnet-integration#limitations)
- Subnet sizing: a `/28` minimum, and "we recommend allocating double the IPs of your planned maximum scale. A `/26` with 64 addresses cover the maximum scale of a single multitenant App Service plan." — [VNet integration: Subnet requirements](https://learn.microsoft.com/azure/app-service/overview-vnet-integration#subnet-requirements)
- An older caveat, now superseded: a 2025 Microsoft Q&A answer said Basic and Standard VNet integration works "only from newer App Service deployments". The current product doc lists Basic without that caveat. — [Microsoft Q&A](https://learn.microsoft.com/answers/a/1889821) vs [current doc](https://learn.microsoft.com/azure/app-service/overview-vnet-integration)

### Inferences
- The design's stated rationale in `docs/infrastructure.md` ("Azure Storage IP rules can't admit an App Service in the same region") is accurate and matches the primary doc.
- The repo's API subnet is `cidrsubnet(vnet_address_space, 2, 0)`, a `/26` from a `/24`, which meets Microsoft's sizing recommendation.
- The same-region Storage limitation also explains why the tfstate account must stay network-open for Microsoft-hosted agents (see Q5). East US 2 is in the US geography that hosted agents draw from, so IP rules would be unreliable even with the published ranges.

## Q5. Pipelines: Microsoft-hosted agents and data-plane access; recommendations for private endpoints; Managed DevOps Pools status and cost

### Takeaway
**Confirms the design's assumptions.** Microsoft-hosted agents have dynamic IPs drawn from every region in the organization's geography, can't join private networks, and aren't covered by the Azure DevOps service tag. For firewalled data planes Microsoft documents three workarounds: allowlist the whole geography's ranges, open the firewall temporarily inside the pipeline, or use self-hosted, scale set or Managed DevOps Pools agents. It explicitly recommends Managed DevOps Pools when allowlisting the whole geography is a concern. Managed DevOps Pools is generally available. Its cost is Azure compute, storage and egress at standard rates plus Azure DevOps self-hosted parallel jobs, the first of which is free. Moving prod to private endpoints with public access disabled requires MDP with VNet injection (or self-hosted agents) at least for prod data-plane steps.

### Cited Findings
- On hosted agent IPs: "Because Azure DevOps uses the Azure global network, IP ranges vary over time. Microsoft publishes a weekly JSON file… Your hosted agents run within the same Azure geography as your organization… allow list the IP ranges for *all* of the regions mapped to your geography." The United States geography covers "Central US, East US, East US 2, North Central US, South Central US, West Central US, West US, West US 2, West US 3". — [Microsoft-hosted agents: Networking](https://learn.microsoft.com/azure/devops/pipelines/agents/hosted?view=azure-devops#networking)
- "You can't use private connections such as ExpressRoute or VPN to connect Microsoft-hosted agents to your corporate network." — [same page](https://learn.microsoft.com/azure/devops/pipelines/agents/hosted?view=azure-devops#networking)
- From the hosted agents FAQ, on Storage SAS or IP errors, the workarounds are: (1) add the hosted agent IP ranges to Storage IP rules; (2) "In your pipeline, use Azure CLI to update the network ruleset for your Azure Storage account right before you access storage, and then restore the previous ruleset"; (3) "Use self-hosted agents or Scale set agents or Managed DevOps Pools." — [Microsoft-hosted agents FAQ](https://learn.microsoft.com/azure/devops/pipelines/agents/hosted?view=azure-devops#faq)
- On security: "When a pipeline needs to access your corporate resources behind a firewall, you have to allow the IP address range for the Azure geography. This may increase your exposure as the range of IP addresses is rather large and since machines in this range can belong to other customers as well." — [Microsoft-hosted agents: Security](https://learn.microsoft.com/azure/devops/pipelines/agents/hosted?view=azure-devops#security)
- From the allow-list doc: "The Service Tag or previously mentioned inbound IP addresses don't apply to Microsoft Hosted agents. Customers are still required to allow the entire geography for the Microsoft Hosted agents. **If allowing the entire geography is a concern, we recommend using the Microsoft Managed DevOps Pools.**" — [Allowed IP addresses and domain URLs](https://learn.microsoft.com/azure/devops/organizations/security/allow-list-ip-url?view=azure-devops#ip-addresses-and-range-restrictions)
- Key Vault on Azure DevOps: "Microsoft services that aren't on the list (for example, Azure DevOps) still need a firewall IP rule, a virtual network rule, or a private endpoint." — [Secure your Azure Key Vault](https://learn.microsoft.com/azure/key-vault/general/secure-key-vault#network-security)
- Agent options: "If you're considering using autoscalable, self-hosted agent pools, we recommend that you consider Managed DevOps Pools." MDP VMs "live in a Microsoft Azure subscription and not in your own Azure subscription." — [Azure Pipelines agents](https://learn.microsoft.com/azure/devops/pipelines/agents/agents?view=azure-devops)
- MDP GA status: the MDP overview has a section titled "**What's new for Managed DevOps Pools GA**". Its items (more regions, Key Vault integration, proxy support, agent IP visibility, move between resource groups and subscriptions, Ubuntu 24.04) match the November 2024 entries in the features timeline. Public preview was announced in sprint 243 (2024). — [Overview of Managed DevOps Pools](https://learn.microsoft.com/azure/devops/managed-devops-pools/overview?view=azure-devops); [features timeline](https://learn.microsoft.com/azure/devops/managed-devops-pools/features-timeline?view=azure-devops#november-2024); [Sprint 243 release notes](https://learn.microsoft.com/azure/devops/release-notes/2024/sprint-243-update#azure-pipelines)
- Recent MDP changes:
  - January 2026: Log Analytics support, image version pinning, and a service tag for control-plane IPs.
  - April 2026: Generation 2 Azure Pipelines images; Generation 1 images "no longer receiving updates".
  - June 2026: pool aliases.
  - November 2025: a public static IP option, because isolated-network pools will get a NAT gateway (extra cost) when Azure default outbound access retires.

  — [MDP features timeline](https://learn.microsoft.com/azure/devops/managed-devops-pools/features-timeline?view=azure-devops#june-2026)
- MDP VNet injection is aimed at agents that "need to access resources that are isolated to private endpoints". Requirements:
  - Delegate a subnet to `Microsoft.DevOpsInfrastructure/pools`; the subnet is then exclusive to that pool.
  - "The pool and virtual network must be in the same region."
  - Grant the DevOpsInfrastructure principal Reader and Network Contributor on the VNet.
  - Avoid `172.17.0.0/16`, which MDP uses internally.

  — [Configure Managed DevOps Pools networking](https://learn.microsoft.com/azure/devops/managed-devops-pools/configure-networking?view=azure-devops#agents-injected-into-existing-virtual-network)
- MDP pricing:
  - It is "a combination of the cost of the Azure services your pool uses, like compute, storage, and data egress, and the standard Azure DevOps Services parallel jobs pricing for self-hosted agents."
  - "Azure DevOps Services provides organizations one free self-hosted parallel job with unlimited minutes."
  - Azure Hybrid Benefit can't be used.
  - Standby agents are billed while online.
  - Microsoft's worked example: a VM at $0.12/hour × 4,000 job-hours ≈ $480/month.

  — [Managed DevOps Pools pricing](https://learn.microsoft.com/azure/devops/managed-devops-pools/pricing?view=azure-devops)

### Inferences
- The repo's current approach matches Microsoft-documented patterns. Terraform does only control-plane (ARM) work from hosted agents. The single data-plane step, the SQL contained-user grant, uses the "open firewall in the pipeline, then restore" pattern, which Microsoft documents for Storage, via `-AddRunnerFirewallRule`. SQL server IP firewall rules don't have Storage's same-region limitation, so this works with SQL. The tfstate account staying network-open with Entra-only auth is a direct consequence of the hosted-agent IP behavior plus the Storage same-region rule.
- With prod on private endpoints and public network access disabled, the temporary-firewall-rule pattern stops working, because SQL won't accept public connections at all. The prod pipeline then needs agents with line-of-sight: an MDP pool injected into a subnet of the prod VNet or a peered VNet, in the same region, or a self-hosted agent. MDP fits a small team best, since Microsoft patches the VMs and only compute, storage and egress plus parallel jobs are billed. A small Linux VM SKU and no standby agents can keep cost near "job-minutes × VM hourly rate".
- If prod gets its own subscription, the MDP pool and its delegated subnet naturally live in the prod subscription or a connectivity VNet peered to it. Non-prod can keep Microsoft-hosted agents.
- Remember MDP's `172.17.0.0/16` reservation and the Windows worker ranges (`172.18`–`172.23`) when planning address space for agent and private-endpoint subnets.

- I found no explicit "GA on <date>" statement on Learn. The GA timing (around November 2024) is inferred from the overview's GA section matching the November 2024 timeline entries.
- I didn't price a specific MDP SKU for eastus2. The figure above is Microsoft's illustrative example.

## Q6. Is Windows App Service still a supported and recommended host for .NET 10 and a static Angular SPA (vs Linux or Static Web Apps)?

### Takeaway
**Partially confirms.** Windows App Service is a supported .NET 10 host: Microsoft says Windows instances ship all supported .NET versions, and a Microsoft response reports .NET 10 installed. I found no deprecation or "prefer Linux" directive. For static client-rendered SPAs, though, Microsoft's hosting guidance points to Azure Static Web Apps ("Use for static web apps that use client-side rendering such as React, Angular…"). App Service is positioned for server compute, so serving the Angular build from IIS on App Service is supported but isn't the service Microsoft names for that job.

### Cited Findings
- "App Service supports languages on both Linux and Windows operating systems." Also: "App Service updates major versions of stacks but can't guarantee any specific minor versions or patch versions… If you need a specific minor or patch version, use a custom container." — [Language runtime support policy for Azure App Service](https://learn.microsoft.com/azure/app-service/language-support-policy)
- "In App Service, the Windows instances already have all the supported .NET Core versions installed." — [Configure an ASP.NET Core app for Azure App Service (Windows)](https://learn.microsoft.com/azure/app-service/configure-language-dotnetcore)
- A Microsoft Q&A answer from Microsoft support staff (secondary, February 2026) says App Service web apps show .NET runtime 10.0.0 installed and that "Patch‑level updates (10.0.2 / 10.0.3) are rolled out by the platform on Azure's own cadence… even though .NET 10 itself is supported". It recommends self-contained publishing or a custom container for an exact patch level. — [Microsoft Q&A](https://learn.microsoft.com/answers/a/12589722)
- Patch updates to .NET "are applied automatically by overwriting the existing installation with the latest version"; new major or minor versions install side by side. — [Azure App Service OS and runtime patching](https://learn.microsoft.com/azure/app-service/overview-patch-os-runtime)
- Microsoft's hosting guide, "Client compute", lists Azure Static Web Apps: "Use for static web apps that use client-side rendering such as React, Angular, Svelte, Vue, and Blazor." Azure App Service is listed under "Server compute" for "typical web hosting… API endpoints, full-stack applications". — [Hosting applications on Azure](https://learn.microsoft.com/azure/developer/intro/hosting-apps-on-azure)
- The JavaScript deployment overview rates Static Web Apps best for "Modern web apps with static frontends, such as React, Vue, or Angular", and App Service for "Full-featured web applications and REST APIs". — [Deployment JavaScript app to Azure overview](https://learn.microsoft.com/azure/developer/javascript/how-to/deploy-web-app#azure-hosting-services-for-javascript-apps)
- Static Web Apps features include globally distributed static content, free SSL, pull-request staging environments, and Entra ID auth integration. — [What is Azure Static Web Apps?](https://learn.microsoft.com/azure/static-web-apps/overview#key-features). A Static Web Apps Standard plan can link an App Service backend, so "/api" is proxied, and "the App Service app only accepts requests that are proxied through the linked static web app." — [API support in Azure Static Web Apps with Azure App Service](https://learn.microsoft.com/azure/static-web-apps/apis-app-service)
- A Microsoft Q&A answer (secondary) recommends Static Web Apps over App Service for an Angular SPA, citing CDN delivery and cost, and quotes Free (500 MB storage, 100 GB/month bandwidth) and Standard (~$9/month) plan limits. — [Microsoft Q&A](https://learn.microsoft.com/answers/a/12496827). Pricing should be confirmed on the official pricing page.

### Inferences
- Hosting the .NET 10 API on Windows App Service is supported and current. The repo's 64-bit worker and framework-dependent or `win-x64` publish align with Microsoft's guidance; self-contained publishing removes dependence on the platform's patch cadence.
- Hosting the Angular build on the same B1 Windows plan adds no compute cost and keeps one toolchain, a defensible trade-off for a small team that has standardized on Windows. Static Web Apps is Microsoft's named fit for client-rendered SPAs and adds CDN and preview environments. That makes it worth recording as an alternative, not a required change.
- If prod later disables public access on the API, consider a Static Web Apps frontend with a linked App Service backend, or Front Door. Static Web Apps' linked-backend lock-down is one documented pattern. This is speculative and outside the current requirements.

### Gaps
- I didn't find an official App Service announcement or runtime matrix that names ".NET 10" on Windows; the evidence is the generic "all supported .NET Core versions installed" statement plus a Microsoft-staff Q&A answer.
- I found no Microsoft statement comparing Windows vs Linux App Service pricing or recommending one OS for new .NET apps, so I can't cite whether Linux B1 is cheaper.
- I didn't verify Static Web Apps private endpoint support or Standard-plan requirements in October 2026.
